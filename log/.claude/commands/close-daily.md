전날 또는 사용자가 지정한 날짜의 기록을 마감한다. 사용자가 `/close-daily` 또는 기록 마감을 요청했을 때만 실행한다. `templates/quick-record.md`, `templates/time-recording.md`, `templates/planning.md`를 참고하되 오늘 계획이나 주간 재계획을 자동 시작하지 않는다. 날짜는 `CLAUDE.md`의 하루 경계를 따른다.

## 가벼운 정리와의 관계

`templates/quick-record.md`로 이미 보관한 일지는 상세 마감의 원본이다. 메모 ID와 원문을 재사용하고 동일 작업·시간을 다시 기록하지 않는다. `<!-- daily-kind: quick -->`가 있고 `<!-- deep-review: complete -->`가 없는 날짜는 파일이 존재해도 상세 마감 완료로 간주하지 않는다. 요청한 날짜의 inbox가 비어 있어도 일지의 빠른 기록으로 세션 분석·요약을 보강할 수 있다. 이 경우 기존 파일의 원문·빠른 기록을 보존하고 `## 상세 마감` 섹션만 추가·갱신한다. 처리 결과를 확인한 뒤에만 deep-review 완료 표식을 남긴다. 미확정 사항은 그대로 표시한다.

## 마감 범위 확인

### 판단 기준

사용자가 날짜를 지정하면 그 날짜(오늘 포함)를 대상으로 한다. 날짜를 지정하지 않았으면 inbox의 명시된 과거 날짜 메모를 먼저 확인하고, `workspace/daily/`에서 오늘보다 이전 날짜 중 빠른 일지만 있고 상세 마감은 끝나지 않은 날을 확인한다. 여러 날짜가 있으면 아래 날짜 범위 확인 규칙을 적용한다.
- 같은 날짜의 Daily Log가 있어도 inbox에 해당 날짜 원문이 남아 있으면 부분 저장 또는 추가 기록일 수 있다. 기존 일지·estimates와 대조해 이미 반영한 부분은 재생성하지 않고 남은 부분만 처리한다. 일지 존재만으로 마감 완료라 단정하지 않는다.
- 없으면 → 마감이 필요하다.

날짜 제목과 문장에 적힌 수행 날짜로 범위가 명확하면 날짜별로 처리한다. 메모 속 미래 일정은 기록 날짜의 새 일정 메모로 보존하며, 미래 날짜에 이미 수행한 기록처럼 처리하지 않는다. 날짜가 없거나 여러 날의 기록이 섞여 분리가 불명확하면 그 부분만 사용자에게 확인하고 `날짜 확인 필요`에 보존한다.

여러 날짜를 처리할 때는 각 원본 범위를 먼저 확보하고 날짜별로 로컬 저장·시간 행 반영·세션 상태 갱신을 수행한다. 모든 대상 저장이 끝난 뒤 처리된 inbox 범위만 정리한다. 일부 저장에 실패하면 원문을 보존하고 재시도에서 기존 결과를 대조해 중복 저장하지 않는다.

마감이 필요한지 최종적으로 한 번 더 거른다. 아래 둘 중 하나라도 있으면 마감 대상이다.
- inbox의 날짜별 자유 메모 또는 대상 날짜 일지의 빠른 기록에 실제 내용이 있다.
- 대상 날짜에 증류할 세션이 하나라도 있다 (아래 `1) 대상 세션 찾기`의 find + 제외 규칙을 먼저 적용한 뒤 남는 세션. inbox가 비어도 Claude Code로만 작업한 날이 여기 걸린다).

둘 다 없으면(빈 양식만 있고 실제 메모와 대상 세션이 없으면) 그날 실질적으로 기록된 게 없다는 뜻이므로 마감 없이 조용히 건너뛴다.

### 마감 절차

대상 기록(위에서 정한 inbox.md 범위)을 기준으로 아래를 수행한다.

#### Input 순서

1. **inbox와 대상 날짜 일지의 빠른 기록 (같은 메모 ID는 한 번만)** — 실제 기록 확인
   사용자의 생각, 결정 이유, 학습, 회고를 확인한다. 이것이 기록의 중심이다. 여기 없는 내용은 만들지 않는다.
   inbox 맨 위 할 일 칸에 처리 안 된 체크나 추가 줄이 있으면 `templates/quick-record.md`의 `오늘 할 일 칸` 절에 따라 먼저 처리하고, 그 결과는 일지의 빠른 기록으로 읽는다. 에이전트가 쓴 할 일 줄은 계획이므로 WHY 출처로 사용하지 않는다.

   자유 메모는 `templates/quick-record.md`의 `inbox 형식`에 따라 문장에서 구분해 아래처럼 쓴다:
   - 한 일·진행·회의 → Daily Log 항목 + Work Item 근거. 함께 적힌 이유는 의사결정 이유·Trade-off로 인식해 Work Item WHY 섹션에 반영한다.
   - 막힘·문제 → 문제 현상·원인·해결 여부 → Trouble Record 후보. 막혀서 진행하지 못한 작업은 tasks.md의 막힘 상태 후보다.
   - 한 줄 인사이트 → Portfolio Seed 후보 (여기선 원본 기록·세션 노트에 보존만 하고, 실제 Portfolio Seed 추출·저장은 `/review-weekly career`가 담당한다)
   - 일정 → 실제 이행 여부 대조용
   - 자연어로 명시한 새 할 일·목표 → 신규 후보. 모호한 표현은 확인 필요로 둔다.
   - 예상·실제 시간 → 시간 기록 출처 (WHY로 쓰지 않는다. `templates/time-recording.md`)
2. **Claude Code 세션 증류** — 대상 날짜에 작업한 세션 transcript에서 사용자의 실제 사고 과정(질문·논의·Trade-off·최종 결정·삽질·인사이트)을 뽑아낸다. 자세한 절차는 아래 `#### Claude Code 세션 증류` 참조. 여기서 나온 증류 노트는 `inbox.md`와 **동급 신뢰도의 WHY 출처**로 다룬다 (사용자가 직접 남긴 사고 과정이므로). 단, 대화 중 결론이 바뀔 수 있으므로 최종 결정은 `확인 및 로컬 저장`에서 확인받는다.
3. **GitHub** (gh CLI 우선, 필요 시 MCP — `collectors/github.md`) — Evidence 연결: 대상 날짜의 Commit(메시지, 날짜), 생성/변경된 PR, 변경된 Issue. 미설정이면 같은 문서의 규칙대로 건너뛰고 로컬 기록만으로 계속한다.
4. **로컬 작업 목록** — `workspace/tasks.md`의 작업 ID와 기존 상태를 확인한다. 경험 후보는 일지에 남긴다.
5. **로컬 월간·주간 목표** — `workspace/tasks.md`에서 상태 변경/신규 추가 후보를 판단한다.

#### Claude Code 세션 증류

목적: 사용자가 손으로 기록하지 않아도, Claude와 함께 작업한 세션 안에 이미 들어 있는 WHY(질문·논의·Trade-off·결정·삽질)를 자동으로 건져 올린다. inbox.md가 비어 있어도 이 단계에서 그날의 사고 과정을 확보할 수 있다.

**1) 대상 세션 찾기**

실제 개발 세션은 이 저장소가 아니라 각 프로젝트 레포에 흩어져 있다. 아래로 대상 날짜에 활동한 transcript를 모은다.

```bash
find ~/.claude/projects -name "*.jsonl" \
  -newermt "{대상날짜} 00:00:00" ! -newermt "{대상날짜+1일} 00:00:00"
```

다음은 **제외**한다.
- 경로에 `/subagents/`가 들어간 transcript → 독립 세션이 아니라 부모 세션의 하위 작업이므로, 부모 세션 증류에 흡수하고 따로 노트를 만들지 않는다.
- 이 저장소 자신의 프로젝트 디렉터리 → 이 도구를 다루는 메타 대화라 개발 성장 기록 대상이 아니다.
- worktree 임시 디렉터리 → 부모 레포 작업과 중복된다.
- 대화가 실질적으로 없는 아주 짧은 세션(사용자 발화 1~2회, 결론 없음) → 증류할 내용이 없으면 노트를 만들지 않는다(inbox의 "실질 내용 없으면 건너뛴다"와 같은 원칙).

**2) 중복 방지**

`workspace/sessions/`(월별 하위 폴더 포함, 재귀로)에 이미 같은 `session_id`를 frontmatter로 가진 노트가 있으면 그 세션은 건너뛴다. (마감 재실행 시 중복 생성을 피하기 위해 확인한다.)

**3) 읽기 요령 (transcript가 크다 — 3MB 이상도 있음)**

통째로 읽지 말고 신호가 있는 줄만 추린다. 사용자 발화와 assistant의 결정·설명만 남기고 도구 호출 로그는 버린다. 아래 명령은 `jq`가 필요하다. `command -v jq`로 먼저 확인하고, 없으면 세션이 없다고 판단하지 않는다. jq가 없다고 한 줄로 알리고 찾은 transcript를 줄 수를 제한해 앞부분부터 직접 읽는다.

```bash
# 사용자 발화만 빠르게 훑기 (content가 문자열/블록배열 둘 다일 수 있음)
jq -r 'select(.type=="user") | .message.content
  | if type=="string" then . else (map(select(.type=="text").text) | join("\n")) end' \
  {세션파일} 2>/dev/null | grep -vE '^[[:space:]]*<(command-|local-command|/)' | head -200
```

여기서 사용자가 무엇을 물었고 무엇을 결정으로 못 박았는지를 축으로 잡고, 그 주변의 assistant 응답에서 Trade-off와 근거를 확인한다. `/effort` 같은 슬래시 명령 래퍼 줄은 신호가 아니므로 무시한다.

**4) 증류 노트 작성**

세션 하나당 `templates/session-distill.md` 형식으로 `workspace/sessions/{YYYY-MM}/{대상날짜}__{project}__{shortid}.md`를 만든다 (대상 날짜의 월 폴더, 없으면 생성). `project`는 프로젝트 디렉터리 이름에서 알아볼 수 있는 레포명(예: `sample-api`), `shortid`는 세션 UUID 앞 8자리를 쓴다. 커밋 해시·PR 언급이 대화에 나오면 Evidence에 함께 적는다.

**5) WHY 파이프라인에 연결**

증류 노트의 `## 다룬 작업` `## Trade-off 고민` `## 최종 결정`은 inbox에 적힌 한 일과 그 이유와 동일하게 Work Item WHY의 재료로 쓴다. `## 막힘·삽질`은 Trouble Record 후보로, `## 인사이트`는 Portfolio Seed 후보(inbox의 인사이트 메모와 동급)로 다룬다. 같은 작업이 inbox.md와 세션 양쪽에 있으면 하나의 Work Item으로 합치고, 근거를 양쪽에서 모은다. (세션 노트 헤더를 매칭할 때는 `templates/session-distill.md`의 괄호 접미사(예: (Work))와 가운뎃점 앞뒤 공백을 무시하고 맞춘다.)

**6) 확인 대상 표시**

노트의 `## 최종 결정` 중 ⚠️가 붙은 항목(대화 중 결론이 바뀌었거나 사용자 확답이 없는 것)과 `## Review Needed`는 아래 `확인 및 로컬 저장`에서 사용자에게 확인한다. 확인 전에는 그 결정을 확정 사실로 저장하지 않는다.

#### 처리

1. **inbox.md와 세션 증류 노트 내용 기반으로 Daily Log를 작성한다.** 이 둘(사용자가 직접 쓴 기록 + 세션에서 뽑은 사고 과정)이 WHY 출처다. 둘 다 없는 내용은 만들지 않는다.
2. **GitHub에서 근거를 찾아 연결한다.** inbox.md 내용에 대응하는 PR, Issue, Commit을 찾아 Evidence로 붙인다.
3. **없는 정보는 생성하지 않는다. Review Needed로 표시한다.**
4. **일정 이행 여부를 확인한다.** 할 일 칸의 고정 일정 줄과 tasks.md의 고정 일정은 메모에 적힌 시각 언급과 대조해 실제 진행 여부를 확인한다. 기록이 없으면 "기록 없음"으로만 표시한다 — 안 지켰다고 단정하지 않는다.
5. **시간 기록을 정리한다.** `templates/time-recording.md`에 따라 예상 또는 실제가 있는 작업을 기록한다. 예상이 없는 실제 소요도 보존하며, 비교 불가능한 기록의 편차는 계산하지 않는다.
6. **tasks.md의 월간 결과·주간 약속·작업의 상태 변경 후보를 찾는다.**
   - 완료/보류/취소: inbox와 빠른 기록에서 기존 항목과 맞는 언급을 찾는다. 고정 일정도 동일하게 다룬다. 그 일정을 진행했다는 증거가 있으면 다녀온 것으로 기록한다. 사유 없는 취소는 Review Needed로 남긴다. 어떤 기존 항목을 가리키는지 애매하면 임의로 매칭하지 않고 Review Needed로 확인한다.
   - 신규 추가: 자연어로 명시한 새 할 일·목표를 인식한다. 기존 작업과 중복이면 연결하고, 불명확하면 후보로 남긴다.
   - 행 삭제 후보는 만들지 않는다.

##### 처리 예시

```
inbox.md:
  목록 조회를 커서 방식으로 결정.
  이유: 목록이 자주 바뀌어 offset이면 중복이 생김.

GitHub:
  PR #7  커서 페이지네이션 구현

↓

Work Item: 목록 조회 페이지네이션 설계
Evidence: PR #7
WHY (inbox.md): 목록이 자주 바뀌어 offset이면 중복이 생김 → 커서 선택
```

#### Trouble Record 승격 기준

inbox의 막힘·문제 메모와 세션 증류의 `## 막힘·삽질`에 있는 항목을 전부 Trouble Record로 올리지 않는다. Trouble Record는 "career 지식으로 남길 값이 있나"가 기준이지 "그날 막혔었나"가 아니다. 아래를 통과한 것만 Daily Log의 `## Trouble Record 후보`에 넣고, 나머지는 세션 노트의 `## 막힘·삽질`에만 남긴다(중복 승격하지 않는다).

승격한다 (실제 엔지니어링 문제):
- 원인과 해결(또는 미해결 상태)이 분명하고 다음에 비슷한 상황에서 다시 통하는 지식
- 데이터·동시성·정합성·설계·성능처럼 도메인이나 시스템에 걸친 문제
- fix 커밋·재오픈 이슈 같은 증거로 뒷받침되면 우선

올리지 않는다 (세션 노트에만 둔다):
- 셸·IDE·린트 일회성 잔손질 (예: 셸 경로 오타, 린트 규칙 위반, IDE 설정)
- 루틴 git 조작 (예: push 거부 후 rebase, 빠뜨린 파일 다시 커밋)
- 프레임워크·도구 quirk (예: 도구 옵션 이름 착오)
- 커뮤니케이션·이해 혼선 (예: 요청 범위를 잘못 이해함)
- 환경 세팅 (예: 패키지 매니저 PATH 누락)

애매하면 승격하지 않고 세션 노트에만 둔다.

#### 금지

- PR/Commit만 보고 의사결정 이유를 생성하지 않는다. (예: PR #7만 보고 "확장성을 위해 커서를 선택했다" 작성 금지.)
- inbox.md와 세션 증류 노트에 없는 내용을 GitHub에서 추론해 Work Item으로 만들지 않는다.
- 세션 증류의 `## 최종 결정` 중 ⚠️ 표시(대화 중 결론이 바뀌었거나 사용자 확답 없음)가 붙은 항목을 확인 없이 확정 사실로 저장하지 않는다. `확인 및 로컬 저장`에서 확인받는다.
- 일정 기록이 없다고 "안 지켰다"고 단정하지 않는다. "기록 없음"으로만 표시한다.
- tasks.md의 항목을 사유 없이 취소 처리하거나 기존 행을 삭제하지 않는다.

#### 출력 형식

```
# 마감 요약 — {대상 날짜}

## 일정 체크
- [x] 10:30 회의 (진행함)
- [ ] 15:00 가스 점검 방문 (기록 없음)

## 시간 추정 vs 실제
| 항목 | 예상 | 실제 | 편차 | 비고 |
|---|---|---|---|---|
| 페이지네이션 구현 | 2h | 2h30m | +30m | - |

## 세션 증류
(대상 날짜에 증류한 세션 목록 — 없으면 "없음")
- {project} {shortid}: {한 줄 요약}  → `workspace/sessions/{YYYY-MM}/{파일명}` (⚠️ 확인 필요 항목 N개)

## Daily Log
- {한 일} — WHY: {inbox.md 또는 세션 증류 근거} / Evidence: {PR #N / session 경로}

## Work Items
### {Work Item 이름}
- 상태:
- 관련 PR:
- WHY (inbox.md):

## Trouble Record 후보
### {제목}
- 신호: {fix commit / 재오픈 / inbox 언급}
- Review Needed: {확인 필요한 질문}

## Review Needed
- {GitHub 항목}: {질문}
```

#### 확인 및 로컬 저장

Review Needed와 세션의 불확실한 최종 결정은 질문으로 모으되 오늘 실행에 필요한 질문만 먼저 묻는다. 답하지 않은 사실은 추정하지 않고 로컬 Daily Log의 Review Needed로 남긴다. 작업·마감에 영향을 주는 미확인은 tasks.md의 해당 항목에도 일지 링크와 함께 남겨 이후 브리핑에서 놓치지 않게 한다. 날짜별 분할이 필요한 경우에는 기존 판단 기준대로 사용자 답을 기다리며 inbox 원문을 보존한다.

이 명령은 Notion에 쓰지 않는다. 경험 후보와 근거는 로컬 일지에 남기고 `/review-weekly career`에서 검토한다. 월간·주간 목표와 작업 상태는 `workspace/tasks.md`에 반영하며, 불확실한 완료·중단은 후보로만 남긴다.

#### 마무리 단계

날짜 범위가 확인되면 아래 순서로 로컬에 저장한다. 날짜가 불명확하면 원문을 보존하고 마감을 보류한다.

1. **로컬 작업 목록 갱신** — 확인된 사실만 `workspace/tasks.md`의 같은 작업 ID에 반영한다. 경험 후보는 Daily Summary에 근거와 함께 보존한다. 반영 뒤 상태가 완료, 취소, 불참인 작업 행과 대상 날짜까지 지난 고정 일정 행을 `workspace/tasks-done.md`의 같은 이름 표 끝으로 옮긴다. 파일이 없으면 `# 끝난 작업`과 두 표의 머리줄로 만든다. 행 내용은 바꾸지 않고 옮긴 ID도 재사용하지 않는다. tasks.md를 바꿨고 보드 날짜가 오늘이면 `workspace/dashboard.md`를 `templates/quick-record.md`의 `보드 파일` 형식으로 다시 쓴다.

2. **inbox.md → daily 파일로 이동** — `workspace/daily/YYYY-MM-DD.md`(대상 날짜)를 생성하고 아래 내용을 저장한다. 이미 같은 날짜 파일이 있으면 덮어쓰지 않는다. 빠른 기록 일지라면 위 규칙대로 같은 파일에 상세 마감만 보강한다. 그 외의 기존 일지는 다음 확인 규칙을 따른다. 기존 파일에 오늘 실행 결과를 추가할지, 별도 파일(`YYYY-MM-DD-2.md`)로 저장할지 사용자에게 확인한다.

   ```md
   # YYYY-MM-DD

   ## 원본 기록
   {inbox.md 전체 내용 (대상 범위)}

   ## 세션 증류
   {대상 날짜에 만든 세션 노트 경로 목록 — 본문은 sessions 폴더에 그대로 두고 여기서는 링크만. 없으면 "없음"}
   - `workspace/sessions/{YYYY-MM}/{파일명}`

   ## Daily Summary
   {생성된 마감 요약 전체}

   ## Review Needed
   {Review Needed 항목 — 없으면 생략}
   ```

3. **estimates.md 누적** — 위 "시간 추정 vs 실제" 표의 각 행을 `workspace/estimates.md` 표 끝에 `| {대상 날짜} | 항목 | 예상 | 실제 | 편차 | 비고 |` 형식으로 append한다. 가벼운 정리에서 같은 메모 ID·시간 항목으로 이미 반영한 행은 추가하지 않는다. 기존 행은 수정·삭제하지 않는다(파일이 없으면 헤더와 함께 생성). 이 파일이 시간 추정 데이터의 단일 출처다.

4. **세션 증류 노트 status 갱신** — 이번 마감에서 확인·반영을 마친 세션 노트의 frontmatter `status`를 `unreviewed` → `reviewed`로 바꾼다. 다음 실행 때 다시 확인 대상으로 올라오지 않게 한다.

5. **처리한 inbox 범위 정리** — daily 파일에 원문이 저장되었는지 확인한 뒤 처리한 날짜 범위만 inbox에서 제거한다. 오늘자·다른 날짜·미확인 기록은 그대로 보존한다. 날짜별 반복에서는 모든 대상 날짜의 저장이 끝난 뒤 한 번만 정리한다. 일부 저장이 실패하면 inbox 원문을 유지하고 이미 저장한 날짜·estimates 행을 다음 실행에서 다시 생성하지 않는다. 확인되지 않은 세션 노트는 `unreviewed`를 유지한다.

## 마감 후 inbox

원문 보존과 처리한 범위 정리가 끝나면 inbox는 날짜별 자유 메모 형식을 유지한다. 미처리 날짜와 `날짜 확인 필요` 기록은 보존한다. 오늘 할 일은 inbox 맨 위 할 일 칸에만 둔다. 기록을 모두 처리했으면 `# Inbox`와 간단한 사용 안내만 남겨도 된다. 마감으로 오늘 작업 상태가 바뀌면 해당 계획 항목만 갱신한다.
